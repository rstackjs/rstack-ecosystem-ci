# Ecosystem CI website

The website uses TanStack Start with SSR on Cloudflare Workers. Rsbuild and
`rsbuild-plugin-cloudflare` build and serve it through `rstack.config.ts` and
the `rs` commands. Both development and production preview run in workerd.

- `pnpm dev`: fetch history and start the development server.
- `pnpm dev:mock`: start with mock data.
- `pnpm dev:cached`: start with previously fetched history.
- `pnpm build`: fetch history and build the Worker and static assets.
- `pnpm preview`: preview the production build locally.
- `pnpm verify:ssr [URL]`: check server-rendered timeline rows and CSS against a
  running server (defaults to `http://localhost:5137`).
- `pnpm deploy`: build and deploy to Cloudflare Workers.
- `pnpm deploy:prebuilt --dry-run`: validate the existing deployment output.

Run these commands from `website/`, or run `pnpm build:website` from the repository
root. Route and Worker binding types are generated by `rs dev` and `rs build`.
History is still fetched from the `data` branch at build time. SSR does not query
GitHub on each request. Dates initially render in UTC and switch to the visitor's
local time zone after hydration.

## Cloudflare Workers

`cloudflare.config.ts` defines the Worker. The Cloudflare plugin writes the
Worker and static assets to `.cloudflare/output`, which `cf deploy --prebuilt`
deploys together. Do not deploy `dist/client` to Pages: this is now an SSR app.
The deployment name is `rstack-ecosystem-ci`.

For local deployment, authenticate with `cf login`, or set
`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. The GitHub `Website` workflow
builds and validates PRs without credentials, and deploys from `main` on website
changes, manual dispatches, and the existing hourly schedule. Set these repository
secrets before merging:

- `CLOUDFLARE_API_TOKEN`: an API token allowed to deploy Workers to the target account.
- `CLOUDFLARE_ACCOUNT_ID`: the target Cloudflare account ID.

The workflow replaces the Pages deploy hook, so
`CLOUDFLARE_PAGES_DEPLOY_HOOK_URL` is no longer used. After validating the first
Worker deployment at its workers.dev URL, move the existing custom domain from
Pages to this Worker in the Cloudflare dashboard and disable the Pages project's
automatic Git deployments. The PR does not change live domains or Pages settings.
If using Workers Builds instead of GitHub Actions, build from the repository root
with `pnpm build:website` and deploy with
`pnpm --filter ecosystem-ci-website deploy:prebuilt`; avoid enabling both automatic
deployment paths.

## Temporary compatibility patch

`pnpm-workspace.yaml` applies
`patches/@tanstack__start-plugin-core@1.171.55.patch`. It embeds the development
asset manifest into the SSR virtual module, so the Worker can read stylesheet
links without sharing the build process's `globalThis`. Unchanged manifests do
not trigger extra rebuilds. See [TanStack/router#8886](https://github.com/TanStack/router/issues/8886).

Remove the patch after upgrading to a TanStack version containing the upstream
fix, and run `pnpm verify:ssr` against both development and production preview.
Rstack 0.9 uses Rsbuild 2.3, which already includes the fix for the SSR define
conflict with web-worker targets; no patch is needed for that issue.
